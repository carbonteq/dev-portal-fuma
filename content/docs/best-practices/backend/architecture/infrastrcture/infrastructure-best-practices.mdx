## Repository Responsibility Patterns

<BestPractice title="Repository Responsibility Patterns">

Keep infrastructure repositories focused on persistence concerns and avoid mixing in domain logic.

## !dont domain-logic-in-repo

**Mix business rules and cross-cutting concerns inside repositories.** This causes:

- Blurred boundaries between domain and infrastructure  
- Hard-to-test domain logic coupled to the database  
- Duplicate rules spread across multiple repositories  

```typescript !example
// File: infra/repositories/user.repository.impl.ts

// ❌ Bad: Repository implementing domain rules
export class UserRepositoryImpl {
  constructor(private readonly db: DbClient) {}

  async updateEmail(userId: UUID, newEmail: string): Promise<void> {
    // This is a domain rule that should be in the domain layer not in the repository
    if (!newEmail.endsWith("@company.com")) {
      // Domain rule lives in infra
      throw new Error("Invalid email domain");
    }
    // infrastructure concerns
    await this.db
      .update(userTable)
      .set({ email: newEmail })
      .where(eq(userTable.id, userId));
  }
}
````

## !do persistence-only-repo

**Keep repositories responsible for data access only.** This provides:

* **Clear separation of concerns** between domain rules and persistence
* **Testable domain logic** without DB dependencies
* **Reusable persistence primitives** across use cases

```typescript !example
// File: infra/repositories/user.repository.impl.ts

export class UserRepositoryImpl {
  constructor(private readonly db: DbClient) {}

  async updateEmail(userId: UUID, email: string): Promise<void> {
    await this.db
      .update(userTable)
      .set({ email })
      .where(eq(userTable.id, userId));
  }

  async findById(userId: UUID): Promise<User | null> {
    const rows = await this.db
      .select()
      .from(userTable)
      .where(eq(userTable.id, userId))
      .limit(1);

    return rows[0] ? rowToEntity(rows[0]) : null;
  }
}

```

</BestPractice>

## Table & Schema Boundary Patterns

<BestPractice title="Table & Schema Boundary Patterns">

Keep table definitions and ORM-specific types inside the infrastructure layer and map them to domain entities.

## !dont leak-table-types

**Expose ORM/table types directly to domain or application code.** This leads to:

* Tight coupling to a specific database/ORM
* Confusion between "row shape" and domain entity
* Painful refactors when schema or tooling changes

```typescript !example
// File: infra/database/tables/user.table.ts
export const userTable = pgTable("users", {
  id: uuid("id").primaryKey(),
  email: varchar("email", { length: 320 }),
  createdAt: timestamp("created_at").defaultNow(),
});

// ❌ Bad: Domain (domain/user/user.entity.ts) depends on Infra (infra/database/tables/user.table.ts).
// This flips the usual dependency direction. In layered architecture, infra is supposed to depend on domain, not the other way around.
import { userTable } from "@infra/database/tables/user.table";

export type UserType = typeof userTable.$inferSelect; // Leaks ORM into domain

export class User {
  constructor(readonly data: UserType) {}
}
```

## !do row-to-entity-mapping

**Map table rows to domain entities inside infra.** This provides:

* **Stable domain model** independent of persistence details
* **Single mapping location** for each entity
* **Flexibility** to change schema or ORM over time

```typescript !example
// File: domain/user/user.entity.ts
export class User {
  constructor(
    readonly id: UUID,
    readonly email: Email,
    readonly createdAt: Date,
  ) {}
}

// File: infra/database/tables/user.table.ts
export const userTable = pgTable("users", {
  id: uuid("id").primaryKey(),
  email: varchar("email", { length: 320 }),
  createdAt: timestamp("created_at").defaultNow(),
});

type UserRow = typeof userTable.$inferSelect;

// File: infra/repositories/user.repository.impl.ts
// create a User entity with domain types instead of just using the DB row type
const rowToEntity = (row: UserRow): User =>
  new User(row.id, Email.of(row.email), row.createdAt);

export class UserRepositoryImpl {
  constructor(private readonly db: DbClient) {}

  async findById(id: UUID): Promise<User | null> {
    const rows = await this.db
      .select()
      .from(userTable)
      .where(eq(userTable.id, id))
      .limit(1);

    return rows[0] ? rowToEntity(rows[0]) : null;
  }
}
```

</BestPractice>

## Migration & Seeding Patterns

<BestPractice title="Migration & Seeding Patterns">

Treat migrations and seeders as an immutable history for your database schema and reference data.

## !dont edit-old-migrations

**Modify existing migration files or write non-idempotent seeds.** This results in:

* Divergent schemas across environments
* Broken rollbacks and unreproducible states
* Hard-to-debug schema drift in CI/production

```typescript !example
// ❌ Bad: Editing an old migration to add a new column
// File: infra/database/migrations/initial_users.ts
export async function up(db: DbClient) {
  await db.schema.createTable("users", (t) => {
    t.uuid("id").primaryKey();
    t.text("email").notNull();
    // Months later:
    t.text("display_name"); // Added afterwards – history changed
  });
}
```

## !do append-only-migrations

**Keep migrations append-only and seeds idempotent.** This ensures:

* **Reproducible schema history** across all environments
* **Safe rollbacks** with clear up/down operations
* **Predictable seed data** for tests and local dev

```typescript !example
// File: infra/database/migrations/initial_users.ts
// Create the initial "users" table.
export async function up(db: DbClient) {
  await db.schema.createTable("users", (t) => {
    t.uuid("id").primaryKey();
    t.text("email").notNull();
  });
}

// Drop the "users" table (rollback for this migration).
export async function down(db: DbClient) {
  await db.schema.dropTable("users");
}

// New migration, not editing an old one.
// File: infra/database/migrations/add_display_name_to_users.ts
// Add "display_name" column to the existing "users" table.
export async function up(db: DbClient) {
  await db.schema.alterTable("users", (t) => {
    t.text("display_name");
  });
}

// Remove "display_name" column (rollback for this migration).
export async function down(db: DbClient) {
  await db.schema.alterTable("users", (t) => {
    t.dropColumn("display_name");
  });
}


// File: infra/services/run-migrations.ts

// Run all pending migrations from the migrations folder.
export async function runMigrations(): Promise<void> {
  await migrate(db, { migrationsFolder: "infra/database/migrations" });
}

```

</BestPractice>

## Configuration & Environment Access Patterns

<BestPractice title="Configuration & Environment Access Patterns">

Centralize configuration in the infra layer and expose a typed config object instead of reading `process.env` everywhere.

## !dont scattered-env-access

**Read `process.env` directly across repositories and services.** This causes:

* Hidden configuration dependencies
* Runtime failures due to missing variables
* Inconsistent parsing and defaulting rules

```typescript !example
// ❌ Bad: Direct env access in repository
export class UserRepositoryImpl {
  private readonly db = new Pool({
    connectionString: process.env.DATABASE_URL, // Unvalidated, untyped
  });
}

// ❌ Bad: Different defaults in different files
const timeout = Number(process.env.DB_TIMEOUT_MS ?? "5000");
const timeout2 = Number(process.env.DB_TIMEOUT_MS ?? "3000");
```

## !do central-config-object

**Use a validated, typed config object from `infra/config`.** This provides:

* **Single source of truth** for configuration
* **Early validation** of required variables at startup
* **Explicit dependencies** in infra components

```typescript !example
// File: infra/config/env.config.ts
import * as S from "@effect/schema/Schema";

const EnvSchema = S.Struct({
  DATABASE_URL: S.NonEmptyString,
  DB_MAX_CONNECTIONS: S.NumberFromString.pipe(S.greaterThanOrEqualTo(1)),
  NODE_ENV: S.Literal("development", "test", "production"),
});

export type AppConfig = S.Schema.Type<typeof EnvSchema>;

export const config: AppConfig = parseEnv(EnvSchema, process.env);

// File: infra/config/index.ts
export { config } from "./env.config";

// File: infra/repositories/user.repository.impl.ts
import { config } from "@infra/config";

export class UserRepositoryImpl {
  private readonly db = new Pool({
    connectionString: config.DATABASE_URL,
    max: config.DB_MAX_CONNECTIONS,
  });
}
```

</BestPractice>
