## What are Boundaries?

In a well-architected backend, your application is divided into **layers**:

- **Client/API Layer**: Where external requests come in (HTTP, GraphQL, webhooks)
- **Domain Layer**: Your business logic, entities, and rules
- **Database Layer**: Where data is persisted (PostgreSQL, MySQL, MongoDB)

The **boundaries** are the interfaces between these layers. Data crosses boundaries when:
- A client sends a request → enters your domain
- Your domain queries the database → DB returns rows
- Your domain sends a response → exits to the client

## The Problem: Type Mismatch at Boundaries

Each layer speaks a different "language" for representing data:

**Clients** send JSON with:
- IDs as plain `string` (no validation - could be any text!)
- Optional fields as `T | null | undefined` (or just missing)
- Dates in multiple formats: `"2024-01-15" (ISO string)`, `1705276800000 (timestamp)`, or `Date` objects
- Inconsistent, unvalidated data

**Domain** needs strict types:
- `UUID` branded type (validated, type-safe identifiers)
- `Option<T>` for explicit optionality (no more null checks everywhere)
- `Date` objects for consistent date handling
- Validated, normalized data

**Database** stores primitives:
- Columns: `uuid`, `text`, `timestamp`, `integer`
- `null` for missing values (no `Option<T>`, no branded types)

**The core problem**: If you directly use client data in your domain or DB rows without transformation, you get:
- ❌ Runtime errors from invalid UUIDs
- ❌ Scattered null/undefined checks throughout your code
- ❌ Date parsing bugs and timezone issues
- ❌ Type unsafe code that compiles but crashes at runtime

## The Solution: Transformation at Boundaries

We use **refined types**, **utility functions**, and **helpers** to transform data as it crosses boundaries:

1. **Refined Types** (`UUID`, `DateTimeFromAny`): Validate and transform raw data
2. **Helper Functions** (`normalizeMaybe`, `optionToMaybe`): Handle optional values consistently
3. **Schemas** (`HostSchema`): Enforce validation at boundaries
4. **Serialization methods**: Convert domain types back to boundary-compatible types

This document shows you exactly how to implement these transformations using a `Host` entity as a real-world example.

## !!steps Step 1 — Concrete Example: Host Entity Type Mismatch

Let's see the problem with a real example. Here's what a `Host` entity looks like from the client's perspective vs what the domain expects:

```typescript !
// Client-facing shape (API DTO)
type HostRequestDTO = {
  id: string;                    // Just a string - could be anything!
  userId: string;                // No validation that it's a valid UUID
  
  // !callout[/createdAt: string \| number \| Date;/] #22c55e Dates arrive in multiple formats: ISO string, timestamp, or Date object
  createdAt: string | number | Date;
  updatedAt: string | number | Date;

  dob?: string | number | Date | null;  // Optional + multiple formats
  phoneNumber?: number | null;           // null vs undefined vs missing
  profileImage?: string | null;

  address?: unknown;
  socialLinks?: unknown;
};

// Domain expectation
import { BaseEntity, IEntity } from "@domain/utils/base.entity";
import { UUID } from "@domain/utils/refined.types";
import { Option as O } from "effect";

interface IHost extends IEntity {
  userId: UUID;                    // Validated, branded UUID type
  dob: O.Option<Date>;            // Normalized to Date, explicit optionality
  phoneNumber: O.Option<number>;  // Explicit optionality with Option<T>
  profileImage: O.Option<string>;
}
````

###### The mismatch is clear:
- Client sends: plain strings, multiple date formats, inconsistent optionals
- Domain wants: branded `UUID`, normalized `Date`, explicit `Option<T>`

The next steps show how to bridge this gap with refined types, schemas, and helper functions.



## !!steps Step 2 — Refined Types: UUID and DateTimeFromAny

Why do we need these? At boundaries, data is messy. The domain needs guarantees:
- UUID: A plain string could be any text. We need validated, properly formatted UUIDs so the domain can trust IDs won't cause database errors or bugs.
- DateTimeFromAny: Dates come as ISO strings, timestamps, or Date objects. The domain needs a consistent `Date` type for date math and comparisons.

These refined types and helper functions validate and transform boundary data:

```typescript !
import * as S from "@effect/schema/Schema";
import { Brand } from "effect/Brand";

// UUID - Refined Types @domain/utils/refined.types
export type UUID = Brand<string, "UUID">;

const UUID_REGEX =
  /^[0-9a-f]{8}-[0-9a-f]{4}-[1-5][0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$/i;

export const StringToUUID = S.transformOrFail(
  S.String,
  S.String.pipe(S.brand("UUID")),
  {
    decode: (value) => {
      if (!UUID_REGEX.test(value)) {
        return ParseResult.fail(new ParseResult.Type(S.String, value));
      }
      return ParseResult.succeed(value as UUID);
    },
    encode: (uuid) => ParseResult.succeed(uuid)
  }
);

// DateTime - Refined Type @domain/utils/date.types
import * as S from "@effect/schema/Schema";

export const DateTimeFromAny = S.transformOrFail(
  S.Union(S.String, S.Number, S.Date),  // Input: loose date formats
  S.Date,                                 // Output: strict Date
  {
    decode: (value) => {
      // Already a Date object
      if (value instanceof Date) return ParseResult.succeed(value);
      
      // Timestamps
      if (typeof value === "number") {
        const d = new Date(value);
        if (Number.isNaN(d.getTime())) {
          return ParseResult.fail(new ParseResult.Type(S.Date, value));
        }
        return ParseResult.succeed(d);
      }
      
      // ISO / other strings
      const d = new Date(value);
      if (Number.isNaN(d.getTime())) {
        return ParseResult.fail(new ParseResult.Type(S.Date, value));
      }
      return ParseResult.succeed(d);
    },
    encode: (date) => ParseResult.succeed(date.toISOString())
  }
);
``` 

Key takeaway: Refined types act as gatekeepers at boundaries:
- They validate incoming data (reject invalid UUIDs, unparseable dates)
- They normalize formats (turn any date format → `Date`)
- They brand types (string → `UUID` with type safety)

`Note`: For a complete list of refined types (UUID, DateTime, Email, etc.), see [Core Utilities → Refined Types](/docs/best-practices/backend/architecture/domain/domain-overview#2-refined-types-refinedtypests).


## !!steps Step 3 — Client Boundary: HostSchema

Why this schema? Raw client JSON can't be trusted. `HostSchema` is the boundary layer that:
- Validates IDs using `StringToUUID` (rejects invalid UUIDs)
- Normalizes dates using `DateTimeFromAny` (converts any format → `Date`)
- Transforms messy input → clean, validated output the domain can safely use

```typescript !
import * as S from "@effect/schema/Schema";
import { StringToUUID } from "@domain/utils/refined.types";
import { DateTimeFromAny } from "@domain/utils/date.types";

export const HostSchema = S.Struct({
  id: StringToUUID,
  createdAt: DateTimeFromAny,
  updatedAt: DateTimeFromAny,

  userId: StringToUUID,
  dob: S.optional(DateTimeFromAny),
  phoneNumber: S.optional(S.Number),
  profileImage: S.optional(S.String),

  address: S.optional(S.Any),
  socialLinks: S.optional(S.Any)
});

export type HostType = S.Schema.Type<typeof HostSchema>;
export type HostSerialized = S.Schema.Encoded<typeof HostSchema>;
```

This schema enforces type safety at the boundary: invalid data is rejected before it reaches the domain.




## !!steps Step 4 — Handling Optional Fields: Maybe&lt;T&gt; Helper

Why this utility? External systems are inconsistent with optional fields. You might receive:
- A real value: `"profile.jpg"`
- `null` (explicitly no value)
- `undefined` (field missing)
- Already an `Option<T>` from another domain

The domain wants consistency: it expects `Option<T>` everywhere. Instead of handling all 4 cases repeatedly, we use the `Maybe<T>` utility:

```typescript !

// @domain/utils/maybe.ts
import { Option as O } from "effect";

export type Maybe<T> = T | null | undefined | O.Option<T>;

export function normalizeMaybe<T>(value: Maybe<T>): O.Option<T> {
  if (O.isOption(value)) return value;
  if (value === null || value === undefined) return O.none();
  return O.some(value);
}

export function optionToMaybe<T>(value: O.Option<T>): T | null {
  return O.getOrNull(value);
}

// @domain/entities/user/host.serialized.ts
type DateInput = string | number | Date;

export type SerializedHost = {
  id: string;
  createdAt: DateInput;         // Accepts loose date formats (will be normalized)
  updatedAt: DateInput;

  userId: string;
  dob: Maybe<DateInput>;        // Accepts any optional format → normalized to Option<Date>
  phoneNumber: Maybe<number>;   // null | undefined | number | Option<number> → Option<number>
  profileImage: Maybe<string>;

  address?: unknown;
  socialLinks?: unknown;
};
```

Helper functions:
- `normalizeMaybe`: Converts any optional format → `Option<T>` (for entering the domain)
- `optionToMaybe`: Converts `Option<T>` → `T | null` (for exiting the domain)

`Note`: See [Domain Overview → Maybe\<T\>](/docs/best-practices/backend/architecture/domain/domain-overview#7-introducing-maybe-t-utility-type) for more details.



## !!steps Step 5 — Domain Entity: Host Constructor

Why this conversion? The domain entity (`Host`) uses strict types internally. The constructor:
- Restores base fields (id, createdAt, updatedAt) from `BaseEntity`
- Casts validated string IDs → `UUID` (safe because validation already happened at schema boundary)
- Normalizes `Maybe<T>` → `Option<T>` using the `normalizeMaybe` helper
- Accepts already-constructed value objects (address, socialLinks)

```typescript !
import { BaseEntity, IEntity } from "@domain/utils/base.entity";
import { UUID } from "@domain/utils/refined.types";
import { Option as O } from "effect";
import { Maybe, normalizeMaybe } from "@domain/utils/maybe";
import { Address } from "./address.vo";
import { SocialLinks } from "./socialLinks.vo";

interface IHost extends IEntity {
  userId: UUID;
  dob: O.Option<Date>;
  phoneNumber: O.Option<number>;
  profileImage: O.Option<string>;
  address: Address;
  socialLinks: SocialLinks;
}

export class Host extends BaseEntity implements IHost {
  userId: UUID;
  dob: O.Option<Date>;
  phoneNumber: O.Option<number>;
  profileImage: O.Option<string>;
  address: Address;
  socialLinks: SocialLinks;

  constructor(data: SerializedHost, address: Address, socialLinks: SocialLinks) {
    super();

    this._fromSerialized({
      id: data.id,
      createdAt: data.createdAt,
      updatedAt: data.updatedAt
    });

    this.userId = data.userId as UUID;
    this.dob = normalizeMaybe(data.dob);
    this.phoneNumber = normalizeMaybe(data.phoneNumber);
    this.profileImage = normalizeMaybe(data.profileImage);
    this.address = address;
    this.socialLinks = socialLinks;
  }

  get hasCompleteProfile(): boolean {
    return (
      O.isSome(this.dob) &&
      O.isSome(this.phoneNumber) &&
      O.isSome(this.profileImage)
    );
  }
}
```

Result: Clean, type-safe domain entity with:
- Branded `UUID` types (can't accidentally use plain strings)
- Normalized `Date` objects (consistent date handling)
- Explicit `Option<T>` (no more null/undefined checks scattered everywhere)


## !!steps Step 6 — Factory Method: Host.create with Domain Validation

Why a factory? The constructor handles type transformations (already normalizes via `normalizeMaybe`). The factory adds domain validation (business rules) before construction. `Host.create` is the safe entry point that:
- Validates business rules (valid DOB, valid phone format) on the boundary data
- Delegates to constructor for type normalization
- Returns a fully validated domain entity

```typescript !
import { HostValidationError, HostGuards } from "./host.error";
import { Address } from "./address.vo";
import { SocialLinks } from "./socialLinks.vo";

export class Host extends BaseEntity implements IHost {
  // properties and constructor from previous step

  static create(serialized: SerializedHost): Host {
    // Validate business rules before construction
    if (!HostGuards.validateDateOfBirth(serialized.dob)) {
      throw new HostValidationError("Invalid date of birth");
    }

    if (!HostGuards.validatePhoneNumber(serialized.phoneNumber)) {
      throw new HostValidationError("Invalid phone number");
    }

    // Create value objects from boundary data
    const address = Address.create(serialized.address);
    const socialLinks = SocialLinks.create(serialized.socialLinks);

    // Constructor handles normalization (Maybe<T> → Option<T>)
    return new Host(serialized, address, socialLinks);
  }
}
```

Separation of concerns:
- Boundary layer (schemas): Type validation and transformation (string → UUID, various formats → Date)
- Factory (`Host.create`): Business rule validation (valid DOB range, phone format) + value object creation
- Constructor: Type normalization (`Maybe<T>` → `Option<T>`)



## !!steps Step 7 — Exiting the Domain: serialize() Method

Why serialize? The domain uses strict internal types (`UUID`, `Option<T>`, `Date`), but external systems expect:
- Plain strings (not branded UUIDs)
- `null` for missing values (not `Option.none()`)
- Serializable date formats
- Plain objects (not value object instances)

The `serialize()` method converts domain types back to boundary-compatible types:

```typescript !
import { optionToMaybe } from "@domain/utils/maybe";

export class Host extends BaseEntity implements IHost {
  // properties, constructor, create

  serialize(): SerializedHost {
    return {
      ...this._serialize(),
      userId: this.userId,
      createdAt: this.createdAt,
      updatedAt: this.updatedAt,
      dob: optionToMaybe(this.dob),
      phoneNumber: optionToMaybe(this.phoneNumber),
      profileImage: optionToMaybe(this.profileImage),
      address: this.address.serialize(),
      socialLinks: this.socialLinks.serialize()
    };
  }
}
```

Boundary transformation (reverse):
- `UUID` → plain `string` (unwrapped from branded type)
- `Option<T>` → `T | null` (via `optionToMaybe` helper)
- `Date` → stays as `Date` (schema's encode can convert to ISO string if needed)
- Value objects → plain objects (via their own `serialize()` methods)



## !!steps Step 8 — Database Boundary: Mapping DB Rows

Why another boundary? The database has its own types:
- Primitive types only (no `Option<T>`, no branded types)
- `null` for missing values
- Plain JSON for nested structures

```typescript !
import { Host } from "@domain/entities/user/host.entity";
import type { SerializedHost } from "@domain/entities/user/host.entity";

type HostRow = {
  id: string;
  created_at: Date;
  updated_at: Date;
  user_id: string;
  dob: Date | null;
  phone_number: number | null;
  profile_image: string | null;
  address: unknown;      // JSON column or joined data
  social_links: unknown; // JSON column or joined data
};

// DB row -> SerializedHost -> Host
export function mapRowToHost(row: HostRow): Host {
  const serialized: SerializedHost = {
    id: row.id,
    createdAt: row.created_at,
    updatedAt: row.updated_at,
    userId: row.user_id,
    dob: row.dob,
    phoneNumber: row.phone_number,
    profileImage: row.profile_image,
    address: row.address,
    socialLinks: row.social_links
  };

  return Host.create(serialized);  // Validation + transformation happens here
}
```

Flow: DB Row (`primitives`, `null`, `JSON`) → SerializedHost (`Maybe<T>`) → Host (`UUID`, `Option<T>`, `Date`, `ValueObjects`)

The same boundary utilities (`normalizeMaybe`, `StringToUUID`, `DateTimeFromAny`) work for both client and database boundaries.

### Key Lessons

1. **Boundary types are not domain types**:
   - Outside the domain, data is usually strings, numbers, nulls, and loosely structured objects.
   - Inside the domain, data is refined (`UUID`), normalized (`Date`), and made explicit (`Option<T>`).

2. **Schemas enforce boundary rules**:
   - `StringToUUID` and `DateTimeFromAny` provide strict decoding at the boundary and deterministic encoding when leaving the domain.

3. **`Option<T>` is the canonical representation for optional values inside the domain**:
   - `normalizeMaybe` accepts any messy external representation (`null`, `undefined`, `Option`, raw) and produces a clean `Option<T>`.

4. **`Maybe<T>` keeps boundary types flexible**:
   - Instead of repeating `T | null | undefined` everywhere, `Maybe<T>` allows external values to be permissive while preserving strictness internally.

5. **Domain and boundary concerns are separate**:
   - The `Host` entity handles domain invariants and exposes a `serialize()` method to produce a consistent outward shape.
   - Boundary schemas handle parsing, coercion, and transformation.
